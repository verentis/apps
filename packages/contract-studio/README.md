# Contract Studio

Install `contract-studio.app.yaml` with Canvas and the Node.js engine. Open Contract Studio, enter a unique code and client-facing title, then create a draft. A `/legal-matters/<code>` link is optional and not dereferenced.

1. Add a point with a short stable ID and original wording. Use `{{client}}` with `client=Example Firm` in confirmed variables, and `{{point:delivery}}` to refer to another point by its stable ID. Moving a point changes its displayed number, not its identity.
2. A library editor can publish a separate cleared revision with jurisdiction, intended use and named approver from the home page. In a draft select a revision to see its base wording. Insert it, select its row and edit the local variation or bindings; the approved base stays visible and unchanged. There is no automatic promotion of client wording.
3. Optionally attach a pinpoint from an installed `/legal-authority-packs/<code>` catalogue. To compare a citation from the former bundled index, install South Africa Law; Studio resolves that old reference against the ZA pack without rewriting the snapshot. Studio only stores whitelisted bibliographic fields, source URL, coverage, revision, rights and retrieval date. It never fetches the URL or inserts source text. For a changed catalogue entry or newer firm revision, use **Compare**, then explicitly accept, reject or defer. Existing local wording is retained; review it against the new base.
4. Submit to validate the points, references and variables. Review the exact rendered wording and provenance table, then return the draft or approve with a reviewer name. Approval freezes the UTF-8 output bytes and SHA-256 digests. **Issue** creates `/legal-client-documents/<code>.txt`, `/legal-client-documents/<code>.fodt` (Flat OpenDocument Text), and `/legal-source-schedules/<code>.json`. Both client files contain only the approved wording. Re-issuing verifies existing artifacts and recreates missing ones from the snapshot, without reading the library or any law pack. Never send the schedule or draft to a client.
5. Copy the issued `.fodt` elsewhere for negotiation, then edit that copy in Office. The Office app manifest registers `.fodt` with MIME `application/vnd.oasis.opendocument.text-flat-xml` in edit mode. Studio does not require Office to issue and does not import edits from negotiation files.

## Limits and permissions

Script checks and conditional writes govern these workflows, not arbitrary VFS clients. Directory write permission can permit direct replacement or deletion, including snapshots, digests, precedents and exports. A digest detects accidental changes; it is not a signature, tamper-proof audit trail or WORM storage. Named approvers are recorded attestations rather than verified identities; there is no enforced separation of duties. Restrict script execution, direct file access (including search, listings and exports), library publication and the schedule directory at the workspace boundary. No per-matter ACL, compliance opinion or source-licensing clearance is implied. Do not share folders containing both private and client files. The agreement list exposes titles to users who can read the contracts container.

Draft commands reject stale viewed versions and require an ETag. Approval is a single conditional write. Issuance is resumable, not a multi-file transaction: an interrupted issue can leave a schedule or document before the agreement is marked issued. Retry from the approved snapshot. A conflicting existing file is never silently replaced. Updates are compared on demand, not monitored in the background. Returned redlines must be reconciled manually; signing and storing executed originals are outside this workflow.

Generate package outputs with `node src/build.mjs`, check them with `node src/build.mjs --check`, and run `node --test tests/*.test.mjs`. The build copies the shared runtime model into each self-contained script bundle.
